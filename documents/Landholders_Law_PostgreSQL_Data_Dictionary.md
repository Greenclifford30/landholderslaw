# Landholders Law — PostgreSQL MVP Data Dictionary

**Document ID:** LL-TECH-DB-002  
**Version:** 0.15 — proposed for review  
**Date:** 2026-11-07  
**Source:** [PostgreSQL data model v1.3](Landholders_Law_PostgreSQL_Data_Model.md)  
**Status:** Draft design, not executable DDL or an approved migration. Target: Amazon RDS PostgreSQL 16+, Python, SQLAlchemy, Alembic; one firm.

> **Draft design refinement:** The [ERD and DDL guide](Landholders_Law_ERD_and_DDL.md#recommended-database-decisions) recommends that `matters.number_allocation_id` uniquely reference the committed allocation instead of duplicating `reference_year` and `reference_sequence` on `matters`. The separate-transaction counter protocol in that guide supersedes the alternative numbering description below for the current DDL draft; it requires concurrency and recovery testing. The snapshot draft adds `sealed_at` and one-way sealing to preserve header/child immutability; the service creates and seals each revision in one transaction and reads only sealed revisions. The guide also describes one-way assignment/grant history. Other dictionary details remain proposed.

This dictionary translates confirmed product decisions into a proposed relational design. Names, status values, constraints and table boundaries here are implementation proposals, not newly approved firm policy. Attorney and Operations must validate template content, legal rules and exception policies. No migration or provider setup is implied by this document.

## Reading the dictionary

- `id` means `bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY`; it is internal. Rows addressable through the API additionally have `public_id uuid NOT NULL UNIQUE`, generated by the application (UUIDv7 preferred); do not treat an identifier as authorization. Tables with no `public_id` are internal. UUIDv7 generation is application-owned for PostgreSQL 16.
- `created_at` / `occurred_at` / `recorded_at` are `timestamptz NOT NULL DEFAULT now()` where listed. Event time is not necessarily transaction commit time. Historical events have a separately nullable actual date or time, never a fabricated timestamp.
- `updated_at` is `timestamptz NOT NULL DEFAULT now()` where listed; a database trigger updates it on every update. `row_version bigint NOT NULL DEFAULT 1` is incremented by the service using optimistic concurrency; zero rows updated means conflict. `?` means nullable for the reason stated; no marker means `NOT NULL`, with no default unless specified. `text` values described as nonblank have `CHECK (btrim(value) <> '')`. All dates are `date`, local times `time without time zone`, instant timestamps `timestamptz`.
- `FK → table` means an explicitly named foreign key, `ON UPDATE RESTRICT ON DELETE RESTRICT`, including optional FKs. Retention is pending; no ordinary application deletion of matter/history data. No cascade is assumed. Supporting FK indexes are required unless an existing PK/unique/index has the FK columns as its leading columns. Name constraints `table_columns_key`, `table_rule_check`, `table_columns_fkey`, indexes `table_columns_idx`; shorten deterministically within PostgreSQL's identifier limit.
- A listed `matter_id` means `bigint NOT NULL FK → matters`. For **every matter-scoped reference**, add `UNIQUE (matter_id,id)` to the referenced table and a composite FK `(matter_id, referenced_id) → (matter_id,id)`; apply the same technique for other ownership pairs specified below. For nullable composite references, use normal `MATCH SIMPLE` plus checks for required target fields. Simple reference columns are `bigint`. Every nullable FK is nullable because the relationship is not yet known or not applicable, not because enforcement is optional.
- `C` is confidential: client, matter, document, address, legal work, correspondence and links. `I` is internal operational metadata; `R` is restricted identity/security metadata. All data is private; classification is a starting point for firm review. Audit payloads must not reproduce document contents, secrets or sensitive URLs. All `jsonb` shapes are versioned and validated; none is a replacement for a core FK.
- Service-only means server-authorized transactional writes, not direct browser access. Database roles deny `UPDATE`/`DELETE` on append-only tables and triggers protect immutable revisions, including child rows. Mutable current state and event insertion must commit together. Role authorization and external identity verification cannot be proven by a CHECK; enforce them in services and test them.
- All status sets and transition rules below are proposed. Use named `CHECK` constraints or managed reference tables as specified, not native enums. `created_by`/`recorded_by`/`actor_user_id` are FKs to `users` unless explicitly nullable for a system event. System actions identify their origin separately; never invent a person.
- Throughput assumption: <500 new matters/year; child and audit volumes, write rates, and retention are unmeasured. The index list is a starting point, not a performance guarantee. No tenant identifier is proposed for the single-firm MVP. Local snapshots contain fictional data only.

## 1. Identity, reference data, and firm settings

### `users` — I/R; app identity and current authorization

**Columns:** `id`, `public_id`, `display_name text` nonblank, `email text` nonblank, `role text DEFAULT 'operations'` (`operations`, `attorney`), `is_admin boolean DEFAULT false`, `is_active boolean DEFAULT true`, `created_at`, `updated_at`, `row_version`. Email is display/contact data, not the identity key. `is_active` is an application block; it cannot replace Workspace verification.

**Integrity/access:** case-insensitive email lookup index, not a uniqueness rule without a confirmed email reuse policy. Only administrators change role/admin flags; append a `user_role_events` row in the same transaction. Login requires verified Workspace membership and current status no older than 15 minutes; fail closed if verification is stale and cannot be refreshed. Provision initial named admin through deployment; authenticate sandbox separately. **History:** deactivate rather than delete; preserve past authority at decision time. **Example:** operations user `Ana`, `is_admin=false`.

### `user_identities` — R; provider binding

**Columns:** `id`, `user_id FK → users`, `provider text` (`google_workspace`, `sandbox`), `issuer text`, `subject text`, `last_verified_at timestamptz?` (never verified), `created_at`. **Constraints:** unique `(provider,issuer,subject)`; unique `(user_id,provider,issuer)`; nonblank issuer/subject. Sandbox identities never authenticate in production. Google subject and verified organization membership, not email, bind identity. **Index:** `user_id`. **Example:** Google issuer and opaque subject.

### `user_role_events` — R; append-only authorization history

**Columns:** `id`, `user_id FK → users`, `actor_user_id FK → users?` (bootstrap/system), `origin text` (`admin`,`bootstrap`), `old_role text?`, `new_role text`, `old_is_admin boolean?`, `new_is_admin boolean`, `reason text?`, `occurred_at`. **Rules:** null actor allowed only for bootstrap with recorded origin; role values as `users`. Preserve actual decision-time role in approval events rather than inferring it from current role. **Index:** `(user_id,occurred_at DESC)`. **Example:** admin grants attorney.

### `firm_settings` — I/R; singleton current configuration

**Columns:** `id smallint PRIMARY KEY DEFAULT 1 CHECK (id = 1)` (singleton exception to identity convention), `timezone text DEFAULT 'America/Chicago'`, `reminder_time time DEFAULT '09:00'`, `historical_cutoff_on date?` (not configured), `updated_by FK → users?` (bootstrap), `updated_at`, `row_version`. Validate timezone against an allowlist/IANA zone database in service. Configuration changes and prior values are written to `audit_events` in the same transaction; cutoff changes flag affected historical records for attorney review. All application administrators may manage reminder schedules. Changing daily time recalculates unsent occurrences without a second reminder already sent that local day; preserve actual/uncertain outcome for an in-flight send and prevent later stale sends where possible. Admin-only. **Example:** cutoff `2026-11-01`.

### `firm_holidays` — I; reminder business calendar

**Columns:** `id`, `holiday_on date`, `name text`, `created_by FK → users`, `created_at`. **Constraints:** unique `(holiday_on)`; nonblank name. All application administrators may manage the calendar; changes are audited and prior entries preserved. Adding a holiday suppresses pending overdue reminders for that date; removing one generates newly eligible overdue reminders if the scheduled time is ahead or they remain eligible for same-local-day retry. Recalculate pending occurrences without backfilling past days. Historical scheduling stores local date and settings used. **Example:** a firm holiday on a weekday.

### `reminder_intervals` — I; advance reminder configuration

**Columns:** `id`, `days_before integer`, `is_active boolean DEFAULT true`, `created_at`. **Constraints:** unique `(days_before)` and `days_before > 0`. Seed 7, 3, 1; all application administrators may change settings, with audit. Changes apply to existing open deadlines, recalculating future unsent reminders without backfilling past advance intervals. Avoid deletion of settings that existing schedules reference. **Example:** `days_before=7`.

### `document_categories`, `deadline_types`, `party_roles` — I; managed classifications

Each has `id`, `code text`, `label text`, `is_active boolean DEFAULT true`, `created_at`, `updated_at`; unique nonblank `code`, nonblank label. Administrator manages and audits changes. Retiring prevents new selections but leaves existing assignments intact; administrators may reactivate. Existing records display the current label; retain label-change history to reconstruct prior labels. Seed `other`, but final labels require review. Other selections require a nonblank matter-specific description for party roles, documents and deadlines. Do not delete catalog rows referenced by historical records. **Example:** document category `contract`, deadline type `financing`.

## 2. Contacts, properties, matters, and access

### `reference_label_events` — I; append-only catalog history

**Columns:** `id`, `document_category_id FK → document_categories?`, `deadline_type_id FK → deadline_types?`, `party_role_id FK → party_roles?`, `action text` (`created`,`renamed`,`retired`,`reactivated`), `old_label text?`, `new_label text?`, `actor_user_id FK → users`, `occurred_at`. Exactly one catalog FK; record changes atomically with the current catalog row. Preserve label history and actor/time; current labels drive display. **Indexes:** each FK with `(occurred_at DESC,id DESC)`. **Example:** administrator renames a deadline type.

### `contacts` — C; reusable people and organizations

**Columns:** `id`, `public_id`, `kind text` (`person`,`organization`), `display_name text` nonblank, `given_name text?`, `family_name text?`, `organization_name text?`, `is_active boolean DEFAULT true`, `created_by FK → users`, `created_at`, `updated_at`, `row_version`. Person display name is required, with given/family names optional; an organization requires its own display/organization name. Nullable name parts allow incomplete person records. Do not require unique names or emails; show possible matches and let staff choose. Authorized staff can inactivate a contact to prevent new selection without deleting links; permit authorized corrections to existing matter details with history and without automatic reactivation. Audit inactivation/reactivation. **Indexes:** `lower(display_name)`; consider `pg_trgm` for measured substring needs. **Example:** person `Jordan Sample`.

### `contact_methods` — C; reusable email/phone

**Columns:** `id`, `contact_id FK → contacts`, `kind text` (`email`,`phone`), `value text` nonblank, `label text?`, `is_preferred boolean DEFAULT false`, `created_at`, `updated_at`. **Constraints:** partial unique `(contact_id,kind) WHERE is_preferred`; `(contact_id,kind,value)` unique only after a normalization policy is agreed. **Index:** `(contact_id,kind)`. Allow shared email/phone values between different contacts; do not impose global uniqueness. Updating contact details prompts review of active matter snapshots. **Example:** preferred email.

### `properties` — C; reusable property identity

**Columns:** `id`, `public_id`, `address_line1 text`, `address_line2 text?`, `city text`, `county text?`, `state text DEFAULT 'IL'`, `postal_code text?`, `property_type text?`, `unit_count integer?`, `is_condominium boolean?`, `created_at`, `updated_at`, `row_version`. Unknown unit count and condo state are meaningful for applicability. **Checks:** `state='IL'`, `unit_count IS NULL OR unit_count > 0`, nonblank address/city. No globally unique address assumption. **Index:** `(lower(city))`; address substring search subject to measurement. **Example:** Illinois street address with unknown units.

### `property_parcels` — C; multiple identifiers per property

**Columns:** `id`, `property_id FK → properties`, `pin text`, `county text?`, `created_at`. **Rules:** PIN nonblank text; preserve formatting and leading zeros. Allow missing county and flag it for follow-up. Preserve original formatting and warn on possible normalized-digit matches; staff decide and no automatic merge or statewide uniqueness is assumed. Prompt staff to update affected active-matter property snapshots after address/PIN corrections and retain prior snapshots. **Index:** `(property_id)` and normalized search only after policy. **Example:** second adjacent parcel. Historical matter PINs belong in `matter_property_snapshots`, not a live join alone.

### `matters` — C; file lifecycle and current transaction state

**Columns:** `id`, `public_id`, `reference_year integer`, `reference_sequence bigint`, `matter_type text?` (`buyer`,`seller`; unknown in draft), `title text?`, `file_status text DEFAULT 'draft'` (`draft`,`open`,`closed`), `transaction_status text DEFAULT 'pending'` (`pending`,`underway`,`closed`,`canceled`), `is_on_hold boolean DEFAULT false`, `contract_signed_on date?`, `contract_price_cents bigint?`, `created_by FK → users`, `created_at`, `updated_at`, `row_version`. **Constraints:** unique `(reference_year,reference_sequence)`; sequence positive; nullable amount nonnegative. Display reference `YYYY-` plus padded sequence; padding is a minimum, not a capacity limit. Drafts need no client/property/workflow yet. **Indexes:** `(file_status,updated_at DESC)`, `(matter_type,file_status)`, legacy references are searched through `matter_legacy_references`. **State:** activate under a matter lock only with type, named client, primary Illinois property with address/city, active authorized primary attorney with current matter access and one published compatible workflow; service creates workflow/tasks and audit atomically. File close/reopen requires reason and actor; transaction closing/canceling is separate. Closed files are read-only for operational changes, including matter-specific corrections; reopen with reason before such edits or assigning follow-up tasks. Authorized hold placement/release, access restriction changes, properly labeled and audited pre-launch historical entries, and recording/reviewing unapproved-send incidents are allowed while closed. A historical document added after closure cannot rewrite earlier readiness or closing decisions; reopen before operational reassessment. Derived primary label precedence: File Closed; otherwise Canceled for a canceled transaction; otherwise Post-Closing Pending for a closed transaction; otherwise Draft; otherwise On Hold; otherwise Closing Scheduled when scheduled; otherwise Active. Show hold and transaction outcome separately where applicable. Reopening a file with a closed transaction shows Post-Closing Pending until file closure. **Example:** `2026-0001`, buyer draft.

### `matter_legacy_references` — C; historical identifiers

**Columns:** `id`, `matter_id`, `label text`, `reference text`, `created_by FK → users`, `created_at`. Nonblank label/reference. A matter can have multiple labeled values; identical references across matters are allowed and all matches shown. Do not require uniqueness until normalization and duplicate behavior within one matter are finalized. **Indexes:** `(matter_id)` and partial-text search on reference. **Example:** prior paper-file number.

### `matter_number_allocations` — I; non-reusable reference reservation

**Columns:** `id`, `reference_year integer`, `sequence_value bigint`, `allocated_at timestamptz DEFAULT now()`, `allocation_token uuid`. **Constraints:** unique `(reference_year,sequence_value)` and `allocation_token`; values positive. Reservations must survive failed matter creation: commit allocation independently before use, with retry keyed by token, or use a nontransactional sequence allocation strategy with equivalent year-scope guarantees. Do not use a transactional counter whose rollback reuses a number. Use the America/Chicago local year when the draft is first saved. Application must tolerate gaps and safely handle crashes. **Example:** year 2026, sequence 1 reserved even after failed create.

### `contact_organization_relationships` — C; reusable person–organization associations

**Columns:** `id`, `person_contact_id FK → contacts`, `organization_contact_id FK → contacts`, `title text?`, `started_on date?`, `ended_on date?`, `created_at`, `updated_at`. Check start/end ordering when known. A person can be linked to multiple organizations; service/constraint trigger verifies person and organization kinds. Keep historical associations rather than overwrite. Partial unique `(person_contact_id,organization_contact_id) WHERE ended_on IS NULL` is a proposed rule, pending overlapping appointment policy. **Indexes:** both FK directions. **Example:** agent affiliated with a brokerage.

### `matter_parties` — C; one contact participation per matter

**Columns:** `id`, `matter_id`, `contact_id FK → contacts`, `is_client boolean DEFAULT false`, `is_primary_client boolean DEFAULT false`, `created_at`. **Constraints:** unique `(matter_id,contact_id)` and `(matter_id,id)`; `NOT is_primary_client OR is_client`; partial unique `(matter_id) WHERE is_primary_client`. Multiple clients and optional one primary client are allowed; designation applies to participation, not a specific role. Activation requires at least one named client, not necessarily a primary. **Indexes:** `(contact_id,matter_id)`, `(matter_id) WHERE is_client`. **Example:** one of two buyer clients.

### `matter_party_roles` — C; multiple roles per participation

**Columns:** `id`, `matter_id`, `matter_party_id`, `party_role_id FK → party_roles`, `other_description text?`, `assigned_by FK → users`, `created_at`, `ended_at timestamptz?`. Composite party FK; `other_description` must be nonblank when the referenced role is Other (enforced by service/constraint trigger because it crosses tables). Partial unique `(matter_party_id,party_role_id) WHERE ended_at IS NULL AND role is not Other` cannot use a joined role predicate in PostgreSQL; implement a stable explicit code or choose an equivalent enforceable key during migration. Multiple distinct roles are allowed. Preserve role assignment history and label snapshots so catalog edits do not rewrite past facts. **Indexes:** `(matter_party_id)`, `(party_role_id)`. **Example:** seller and executor roles for one person.

### `matter_party_organization_snapshots` — C; historical affiliation

**Columns:** `id`, `matter_id`, `matter_party_snapshot_id`, `organization_contact_id FK → contacts?` (identity unavailable), `organization_name text`, `relationship_label text?`, `recorded_at`. Composite FK to matter-party snapshot, which needs `UNIQUE (matter_id,id)`; nonblank organization name. Preserve historical affiliation even when contact relationship changes; service validates organization kind if linked. **Index:** `(matter_party_snapshot_id)`. **Example:** agent's brokerage at transaction time.

### `contact_merges` and `contact_merge_items` — C/R; traceable consolidation

`contact_merges`: `id`, `source_contact_id FK → contacts`, `target_contact_id FK → contacts`, `status text` (`completed`,`correction_required`,`corrected`), `performed_by FK → users`, `performed_at`, `resolution jsonb` (versioned selected field outcomes), `reason text?`; source differs from target. Service locks both records, rejects different kinds/cycles and records a durable redirect/tombstone without deleting source; audit transaction and preserve all matter snapshots. `contact_merge_items`: `id`, `contact_merge_id FK → contact_merges`, `matter_id FK → matters?` (non-matter item), `item_type text`, `source_id bigint`, `target_id bigint?`, `recorded_at`; describes affected associations and conflicts without replacing actual FKs. Merge preview shows only matters user may access; it must not reveal hidden matter existence, counts, conflict messages or timing. A privileged server transaction can consolidate inaccessible associations while preserving their snapshots; audit records and merge-item visibility must obey matter restrictions. Person/organization merge is prohibited. Any authorized staff may merge after reviewing visible affected matters and resolving available conflicts; restricted association conflicts must be handled without disclosure, with an authorized administrator correction path if necessary. A correction is administrator-led, append-only/audited, not a blind rollback of later changes. Define conflict-safe role/primary-client consolidation and lock order before implementation. **Indexes:** `(source_contact_id)`, `(target_contact_id)`, `(contact_merge_id)`. **Example:** two person records merged; restricted matter snapshot unchanged.

### `matter_party_snapshots` — C; immutable matter-time details

**Columns:** `id`, `matter_id`, `matter_party_id`, `revision integer`, `display_name text`, `source_contact_updated_at timestamptz?`, `recorded_by FK → users`, `recorded_at`, `reason text?`. Composite FK to party; unique `(matter_party_id,revision)`, revision > 0. **Index:** `(matter_party_id,revision DESC)`. Create on add and when staff accepts an update, not automatically. Name history and corresponding child methods remain immutable. **Example:** prior client name.

### `matter_party_snapshot_methods` — C; methods used at a snapshot

**Columns:** `id`, `snapshot_id FK → matter_party_snapshots`, `kind text` (`email`,`phone`), `value text`, `label text?`, `is_preferred boolean DEFAULT false`. **Constraints:** nonblank value; `(snapshot_id,kind,value)` unique; partial unique `(snapshot_id,kind) WHERE is_preferred`. Immutable with parent. **Example:** email used on prior revision.

### `matter_properties` — C; property participation

**Columns:** `id`, `matter_id`, `property_id FK → properties`, `is_primary boolean DEFAULT false`, `created_at`. **Constraints:** unique `(matter_id,property_id)`; partial unique `(matter_id) WHERE is_primary`; unique `(matter_id,id)`. At most one primary does not guarantee one: activation checks existence. **Example:** primary subject property.

### `matter_property_snapshots` and `matter_property_snapshot_parcels` — C; immutable transaction facts

`matter_property_snapshots`: `id`, `matter_id`, `matter_property_id`, `revision integer`, `address_line1 text`, `address_line2 text?`, `city text`, `county text?`, `state text`, `postal_code text?`, `property_type text?`, `unit_count integer?`, `is_condominium boolean?`, `recorded_by FK → users`, `recorded_at`, `reason text?`. Composite matter FK, unique `(matter_property_id,revision)`, `state='IL'`, positive revision and optional unit count. `matter_property_snapshot_parcels`: `id`, `snapshot_id FK → matter_property_snapshots`, `pin text`, `county text?`, nonblank PIN. **Indexes:** `(matter_property_id,revision DESC)` and `(snapshot_id)`. Corrections append snapshots and trigger rule reevaluation. **Example:** property address plus two parcel rows.

### `matter_assignments` — C/I; staff responsibility and history

**Columns:** `id`, `matter_id`, `user_id FK → users`, `assignment_role text` (`attorney`,`operations`), `is_primary boolean DEFAULT false`, `started_at timestamptz DEFAULT now()`, `ended_at timestamptz?`, `assigned_by FK → users`, `reason text?`. **Checks:** end not before start. Partial unique `(matter_id,assignment_role) WHERE is_primary AND ended_at IS NULL`; partial unique `(matter_id,user_id,assignment_role) WHERE ended_at IS NULL`. **Indexes:** `(user_id,ended_at)`, `(matter_id,ended_at)`. Assignment changes close old row and add new row; Activation requires an active primary attorney with matter access. If the primary attorney becomes inactive, loses Attorney role or matter access, keep the matter active but flag it as needing an authorized primary attorney; readiness is Not Ready until one is assigned. Any authorized attorney with matter access may approve correspondence or exceptions; assignment is not required. **Example:** primary assigned attorney.

### `matter_access_grants` — R; explicit restriction access

**Columns:** `id`, `matter_id`, `user_id FK → users`, `granted_by FK → users`, `granted_at timestamptz DEFAULT now()`, `revoked_by FK → users?`, `revoked_at timestamptz?`, `reason text?`. Partial unique `(matter_id,user_id) WHERE revoked_at IS NULL`; revoked actor/time must be both null or both present, and revocation cannot precede grant. A separate `matters.is_restricted boolean NOT NULL DEFAULT false` controls default access: unrestricted allows active staff; restricted allows active grants, subject to audited administrator recovery. Any authorized staff can change restrictions; when applying a restriction, grant the acting user access initially in the same transaction. They may later remove their own access. Recovery of a locked-out matter is administrator-only and audited. Lock and audit changes; mark inaccessible deadline owners for reassignment. **Indexes:** `(user_id,matter_id) WHERE revoked_at IS NULL`. **Example:** grant access to assigned attorney.

### `matter_lifecycle_events` — C; append-only file/transaction events

**Columns:** `id`, `matter_id`, `event_type text` (`activated`,`held`,`resumed`,`transaction_closed`,`transaction_canceled`,`file_closed`,`file_reopened`), `reason text?`, `actor_user_id FK → users`, `occurred_at`. Require nonblank reason for close, reopen and cancellation; service validates permitted transitions, disposition of outstanding work and updates matter in same transaction. **Index:** `(matter_id,occurred_at DESC)`. **Example:** file reopened after cancellation.

### `matter_legal_holds` — C/R; independent preservation obligations

**Columns:** `id`, `public_id`, `matter_id`, `reason text`, `status text DEFAULT 'active'` (`active`,`released`), `placed_by FK → users`, `placed_at timestamptz DEFAULT now()`, `released_by FK → users?`, `released_at timestamptz?`, `release_reason text?`, `created_at`, `updated_at`, `row_version`. Nonblank placement reason; release requires attorney, release timestamp and nonblank reason; unreleased rows have all release fields null. Unique `(matter_id,id)`; multiple independent holds allowed. Either authorized role may place; only attorney may release. No deletion/purge of matter and associated records/files while any hold is active. Changes and actor/time are auditable; use locking to serialize holds with purge and object onboarding. Hold does not by itself prevent edits or file closure. **Indexes:** `(matter_id,status)`. **Example:** two independent holds on a closed file.

### `legal_hold_object_protections` — R/C; external storage enforcement progress

**Columns:** `id`, `matter_id`, `document_version_id`, `status text` (`pending`,`protected`,`release_pending`,`released`,`failed`), `provider_object_version_id text`, `last_checked_at timestamptz?`, `failure_code text?`, `created_at`, `updated_at`, `row_version`. Composite FK to uploaded document version; unique `(matter_id,document_version_id)`; provider ID must match immutable version. This is application reconciliation state, not proof by itself: verify provider state, retain attempt/outcome events and alert on failures. A matter may have multiple independent holds; S3 object legal hold is object-level, so derive effective protection from *all* active holds and never release while any apply. Place hold in DB immediately, show protection pending until all applicable object versions are confirmed protected; external-only content yields partial protection and a retained-copy request. Uploads on held matters stay unavailable until scan passes and storage protection is confirmed. Serialize new uploads and hold/release changes via matter-level lock and use an outbox and idempotent worker; S3 and PostgreSQL cannot commit atomically. Define S3 Object Lock enablement, existing-object migration, permission isolation, version-level events, reconciliation and failure/compensation procedures before deployment. **Indexes:** `(matter_id,status)` and `(status,updated_at)` for reconciliation. **Example:** uploaded version awaiting S3 protection.

### `legal_hold_protection_events` — R; append-only provider attempts

**Columns:** `id`, `legal_hold_object_protection_id FK → legal_hold_object_protections`, `action text` (`apply`,`verify`,`release`), `outcome text` (`started`,`confirmed`,`failed`,`uncertain`), `error_code text?`, `recorded_at`. No secrets or signed URLs. Retry failures and alert administrators; retain uncertainty until verified. **Index:** `(legal_hold_object_protection_id,recorded_at DESC,id DESC)`. **Example:** S3 hold applied and verified.

## 3. Workflow definitions and execution

### `workflow_templates` — I; buyer/seller identity

**Columns:** `id`, `code text`, `name text`, `matter_type text` (`buyer`,`seller`), `created_at`. Unique code, nonblank name/code. **Example:** `IL_BUYER`.

### `workflow_template_versions` — I; versioned immutable definitions

**Columns:** `id`, `workflow_template_id FK → workflow_templates`, `version integer`, `status text` (`draft`,`published`,`retired`), `published_at timestamptz?`, `created_at`. Unique `(workflow_template_id,version)`, positive version; draft has null publication time, published/retired require it. Publish and retire are controlled transitions. Publication locks and validates child definitions; after publication their content is immutable, retirement may change status only. **Example:** buyer v1 published.

### `workflow_template_validation_events` — I/R; attorney validation history

**Columns:** `id`, `workflow_template_version_id FK → workflow_template_versions`, `action text` (`validated`,`withdrawn`), `attorney_user_id FK → users`, `reason text?`, `occurred_at`. Require a reason for withdrawal; serialize validation changes with publication and readiness evaluation. Attorney authority is checked at the event time. Latest effective event determines validation; retirement alone does not withdraw it. Published unvalidated versions may be instantiated, but readiness is Not Ready with a template-validation reason. Withdrawal flags affected matters for review. **Index:** `(workflow_template_version_id,occurred_at DESC,id DESC)`. **Example:** attorney validates buyer v1.

### `workflow_phases` — I; versioned task grouping

**Columns:** `id`, `workflow_template_version_id FK → workflow_template_versions`, `phase_key text`, `name text`, `sort_order integer`. Unique `(workflow_template_version_id,phase_key)` and `(workflow_template_version_id,id)`; nonblank key/name. **Example:** `financing`.

### `workflow_task_templates` — I; standard task definition

**Columns:** `id`, `workflow_template_version_id FK → workflow_template_versions`, `workflow_phase_id bigint`, `task_key text`, `title text`, `description text?`, `sort_order integer`, `is_required boolean DEFAULT true`, `applicability_rule jsonb?` (unconditional when null). ### `tasks` — C; current work and provenance

**Columns:** `id`, `public_id`, `matter_id`, `matter_workflow_id bigint?` (manual task need not have a template), `workflow_template_version_id bigint?`, `workflow_task_template_id bigint?`, `source text` (`standard`,`manual`), `title text`, `description text?`, `assigned_to FK → users?` (unassigned), `status text DEFAULT 'pending'` (`pending`,`in_progress`,`waiting`,`under_review`,`blocked`,`completed`,`canceled`,`waived`), `applicability text DEFAULT 'applicable'` (`applicable`,`inapplicable`,`unresolved`), `is_required boolean`, `due_on date?`, `due_time time?`, `due_timezone text?`, `due_utc_offset_seconds integer?`, `due_at timestamptz?`, `created_by FK → users`, `created_at`, `updated_at`, `row_version`. `due_time` requires date, timezone, resolved UTC offset and due instant; default the timezone to America/Chicago for timed tasks while permitting explicit zones. Standard requires workflow/version/template all present; manual has no template provenance (workflow link policy to be finalized). Composite FKs ensure task and workflow share matter and workflow/version and task template share version. Partial unique `(matter_workflow_id,workflow_task_template_id) WHERE source='standard'`; unique `(matter_id,id)`. **Indexes:** `(assigned_to,due_on)` partial over open states; `(matter_id,status)`. Either role may reopen with a reason. Waiting/Blocked requires a reason; direct pending→completed is allowed with actor/time. A new completion requires current effective applicability `applicable` and all dependencies satisfied or resolved as described below. Completion and dependency checks run under coordinated locks. Reopening a task that supplied accepted evidence reopens the corresponding requirement for reassessment. A task has at most one accountable owner and may be unassigned. Assignment requires an active user with matter access; loss of access or inactive status flags the task for reassignment. Reassigning while Waiting, Blocked or Under Review preserves state and records the change. **Example:** required financing follow-up with date only.

### `task_events` — C; append-only work, disposition and applicability history

Assignment has one accountable owner, and active matter access is checked at assignment and notification viewing. `task_assignment_notification_items.assignment_event_id` references this table, not generic task events. **Indexes:** `(task_id,occurred_at DESC,id DESC)`, both owner FKs. **Example:** task moves from one Operations user to another while Blocked.

### `task_rule_evaluations` — C; explain conditional decisions

**Columns:** `id`, `matter_id`, `task_id`, `workflow_task_template_id FK → workflow_task_templates`, `result text` (`applicable`,`inapplicable`,`unresolved`), `facts jsonb`, `rule_version integer`, `actor_user_id FK → users?` (system evaluation), `evaluated_at timestamptz DEFAULT now()`. Composite task FK; service verifies task/template provenance and records allowable source fact versions; never execute stored code. **Index:** `(task_id,evaluated_at DESC)`. **Example:** unknown unit count → unresolved.

### `applicability_overrides` — C; manual decision and review history

**Columns:** `id`, `matter_id`, `task_id bigint?`, `requirement_id bigint?`, `decision text` (`applicable`,`inapplicable`), `reason text`, `actor_user_id FK → users`, `decided_at timestamptz DEFAULT now()`. Exactly one typed matter-scoped FK; reason nonblank. Either authorized role may override rule-based task or requirement applicability, except only an attorney can mark a non-waivable requirement inapplicable. Preserve rule result and manual decision separately. Relevant fact changes flag the override for review instead of silently replacing it; effective applicability becomes unresolved until reviewed and blocks completion/dependency/readiness where applicable. Store source fact/rule versions and review history; service locks relevant rows and updates the current projection atomically. **Indexes:** `(task_id,decided_at DESC)` and `(requirement_id,decided_at DESC)`. **Example:** attorney marks a non-waivable requirement inapplicable with reason.

### `applicability_override_events` — C; append-only review disposition

**Columns:** `id`, `matter_id`, `applicability_override_id`, `event_type text` (`review_required`,`confirmed`,`replaced`), `reason text`, `actor_user_id FK → users?` (system review flag), `occurred_at`; composite matter FK to override (add unique `(matter_id,id)`); nonblank reason; null actor only for system review flag. Retain old/new rule evaluations and reapply attorney-only rule on nonwaivable inapplicability. **Index:** `(applicability_override_id,occurred_at DESC,id DESC)`. **Example:** source fact change requests review.

### `task_dependencies` — C; same-matter prerequisite edge

**Columns:** `id`, `matter_id`, `task_id`, `depends_on_task_id`, `created_at`. Two composite FKs to tasks; unique `(task_id,depends_on_task_id)`; `task_id <> depends_on_task_id`. **Indexes:** `(depends_on_task_id)`, `(matter_id,task_id)`. Service serializes graph edits per matter (e.g. transaction advisory lock) before cycle detection; a plain transaction is insufficient. Completion requires each prerequisite completed or appropriately waived; a recorded inapplicable result also permits proceeding, while unresolved applicability blocks. A canceled prerequisite does not satisfy the edge: flag for review and let either role resolve it with a reason. A completed dependent stays completed if a prerequisite is reopened, but flag the edge for review. Resolving an edge never satisfies a separate closing requirement. **Example:** closing package depends on title review.

### `task_dependency_events` — C; dependency review and resolution

**Columns:** `id`, `matter_id`, `task_dependency_id`, `event_type text` (`review_required`,`resolved`,`reactivated`), `reason text`, `actor_user_id FK → users?` (system review flag), `occurred_at`. Add `UNIQUE (matter_id,id)` to `task_dependencies` and use composite FK; nonblank reason; null actor only for system-generated review flag. Either authorized role may resolve a canceled prerequisite dependency with a reason; a reopened prerequisite can flag an already-completed dependent without undoing completion. Define current dependency resolution as the latest effective event, with ties ordered by id; changing the edge does not change a closing requirement. **Index:** `(task_dependency_id,occurred_at DESC,id DESC)`. **Example:** canceled duplicate prerequisite resolved for dependent work.

## 4. Deadlines, closing, issues, and financial confirmation

### `deadlines` — C; current effective date

**Columns:** `id`, `public_id`, `matter_id`, `deadline_type_id FK → deadline_types`, `other_type_description text?`, `title text`, `kind text` (`contractual`,`internal`), `status text` (`open`,`satisfied`,`canceled`,`superseded`), `due_on date`, `due_time time?`, `timezone text DEFAULT 'America/Chicago'`, `due_utc_offset_seconds integer?`, `due_at timestamptz?`, `owner_user_id FK → users?`, `reminders_enabled boolean DEFAULT true`, `created_by FK → users`, `created_at`, `updated_at`, `row_version`. Unique `(matter_id,id)`; title nonblank. Other type requires a nonblank description; check through service/constraint trigger because the catalog is a separate table. Deadline type changes require a reason, preserve prior classification and make linked open issues unassessed; update atomically. Overdue is derived from date/time, not a persisted status. Date-only becomes operationally overdue the next local day; no legal cutoff is implied. Timed deadlines become overdue after the recorded cutoff instant. Resolve ambiguous/nonexistent local times explicitly before saving and retain the selected offset and instant on the current row and every revision; validate consistency. Deadline assignment requires an active user with matter access. Unowned/inaccessible owner is flagged for authorized staff. **Indexes:** `(due_on,matter_id) WHERE status='open'`, `(owner_user_id,due_on)`. Each edit, source and effective date revision is atomic with `deadline_revisions`. **Example:** financing date without cutoff.

### `deadline_assignment_events` — C; accountable ownership changes

**Columns:** `id`, `matter_id`, `deadline_id`, `previous_user_id FK → users?`, `new_user_id FK → users?`, `actor_user_id FK → users?` (automated assignment), `origin text` (`user`,`system`), `reason text?`, `occurred_at`. Composite deadline FK; unique `(matter_id,id)`; at least one owner is present and old/new are distinct using `IS DISTINCT FROM`; user origin requires actor. Service checks the new owner is active and has matter access, uses the same lock for assignment and current-owner update, and retains history. An unassigned, inactive-owner or inaccessible-owner deadline remains visible to authorized staff for claiming; it does not automatically suspend or stop the clock. **Indexes:** `(deadline_id,occurred_at DESC,id DESC)` and both user FKs. **Example:** Operations takes over a financing deadline.

**Recommended MVP assignment notices:** In-app notice to the new owner on initial assignment and reassignment; notify the previous owner on reassignment or unassignment if still active and authorized. Skip the actor's new-owner notice on self-assignment but still notify an eligible previous owner. Group multiple automatic assignments from the same workflow activation by recipient and matter, linking the individual deadlines; do not disclose restricted matters. On deadline date/time/timezone/source changes, notify the currently authorized owner in-app, except skip an actor notifying themself; preserve full revision history and leave periodic email/in-app reminder schedules unchanged. No email for these assignment/change notices by default. These are proposed operational defaults, not legal timing rules or replacements for reminders.

### `deadline_assignment_notification_items` — C; linked grouped notices

**Columns:** `id`, `matter_id`, `notification_id`, `deadline_id`, `assignment_event_id`, `created_at`. Composite same-matter FKs to notification, deadline and `deadline_assignment_events`; unique `(notification_id,deadline_id,assignment_event_id)`; service verifies event belongs to deadline. A versioned event key and recipient/kind ensure idempotent grouping; recheck authorization when notices are created and read. Date-change notices reference the specific deadline revision in a separate typed link or notification target; finalize target uniqueness in migration. Write ownership change, history, notification intent and outbox atomically; worker delivery remains idempotent. The once-per-local-day limit applies to scheduled deadline reminders, not assignment/change notices; do not suppress a critical ownership change because an overdue reminder was already sent. **Indexes:** notification, deadline and event FKs. **Example:** one activation notice for several newly assigned deadlines.

### `deadline_revisions` — C; append-only effective values and source

**Columns:** `id`, `matter_id`, `deadline_id`, `revision integer`, `deadline_type_id FK → deadline_types`, `other_type_description text?`, `due_on date`, `due_time time?`, `timezone text`, `due_utc_offset_seconds integer?`, `due_at timestamptz?`, `source_document_version_id bigint?`, `source_note text?`, `reason text`, `actor_user_id FK → users`, `recorded_at`. Composite FKs to deadline and optional document version within matter; unique `(deadline_id,revision)`, positive revision, nonblank reason. Both source fields can be null but must surface a missing-source flag for contractual deadlines. Create initial revision as well as changes; update current row and revision atomically. **Index:** `(deadline_id,revision DESC)`. **Example:** confirmed extension with source note.

### `deadline_extension_requests` — C; pending extension is not effective change

**Columns:** `id`, `matter_id`, `deadline_id`, `proposed_due_on date`, `proposed_due_time time?`, `status text` (`pending`,`confirmed`,`rejected`,`withdrawn`), `requested_by FK → users`, `requested_at timestamptz`, `resolved_at timestamptz?`, `note text?`. Composite FK to deadline. Resolved state requires resolution timestamp; confirmation creates a deadline revision atomically; pending does not change effective deadline. **Index:** `(deadline_id,status)`. **Example:** requested Tuesday extension still pending.

### `closing_events` — C; appointment and actual transaction outcome

**Columns:** `id`, `matter_id`, `event_type text` (`scheduled`,`rescheduled`,`closed`,`canceled`), `scheduled_at timestamptz?`, `scheduled_timezone text?`, `scheduled_utc_offset_seconds integer?`, `location text?`, `actual_at timestamptz?`, `reason text?`, `actor_user_id FK → users`, `recorded_at`. Require scheduled timestamp, timezone and selected offset for scheduling events; reject nonexistent local times and require staff choice for ambiguous times; actual timestamp for recorded outcome only if known—historical outcomes may be unknown and must be marked historical (add `is_historical boolean DEFAULT false`). Close/cancel reason policy per lifecycle. Append-only; derive current schedule/outcome, or maintain an explicitly synchronized current pointer using same-matter FK. **Index:** `(matter_id,recorded_at DESC)`. **Example:** reschedule with new instant/location.

### `closing_milestone_links` — C; internal date offsets

**Columns:** `id`, `matter_id`, `task_id bigint?`, `deadline_id bigint?`, `offset_days integer`, `offset_basis text DEFAULT 'calendar'` (`calendar`,`business`), `is_active boolean DEFAULT true`, `created_at`. Composite FKs, `num_nonnulls(task_id,deadline_id)=1`; service only permits an internal deadline, never a contractual one. Reschedule proposes calculated changes for staff confirmation and audits committed revisions. **Indexes:** `(matter_id,is_active)` and target FKs. **Example:** internal task two calendar days before closing. Business-day offsets use the administrator-managed firm holiday calendar. Calendar-day results remain on weekends/holidays. On rescheduling, show proposed changes and save only after staff confirmation.

### `matter_issues` — C; independently actionable blockers

**Columns:** `id`, `public_id`, `matter_id`, `title text`, `issue_type text`, `status text` (`open`,`blocked`,`resolved`,`canceled`), `severity text` (`low`,`normal`,`high`), `owner_user_id FK → users?`, `deadline_id bigint?`, `description text?`, `resolution text?`, `readiness_impact text DEFAULT 'unassessed'` (`unassessed`,`blocking`,`nonblocking`), `created_at`, `updated_at`, `row_version`. Composite deadline FK; resolution required when resolved. An open unassessed issue blocks readiness until either authorized role records an assessment. Relevant changes to details, severity, status or linked deadline (including deadline revisions) make the assessment stale; owner-only changes do not. Resolving an issue records its resolution and removes its readiness block without a new assessment; cancellation with a recorded reason also removes the block. Reopening either a resolved or canceled issue requires a new assessment. Preserve assessment, reason, actor and time in append-only issue assessment events; issue attachments use a matter-scoped join to documents if required in final schema. **Index:** `(matter_id,status)`. **Example:** title exception awaiting resolution.

### `issue_readiness_assessments` — C; append-only readiness impact

**Columns:** `id`, `matter_id`, `matter_issue_id`, `impact text` (`blocking`,`nonblocking`), `reason text`, `actor_user_id FK → users`, `assessed_at timestamptz DEFAULT now()`. Composite matter FK; nonblank reason. Serialize assessment and current issue update; an unassessed open issue makes the matter Not Ready. Either authorized role may assess; attorney authorization remains required for exceptions to required items. **Index:** `(matter_issue_id,assessed_at DESC,id DESC)`. **Example:** attorney records why a title issue is nonblocking.

### `financial_confirmations` and `financial_confirmation_revisions` — C; no ledger

`financial_confirmations`: `id`, `public_id`, `matter_id`, `kind text` (`retainer`,`earnest_money`,`closing_payment`,`other`), `created_by FK → users`, `created_at`; unique `(matter_id,id)`; several confirmations of the same kind allowed. `financial_confirmation_revisions`: `id`, `matter_id`, `financial_confirmation_id`, `revision integer`, `status text` (`expected`,`confirmed`,`corrected`,`canceled`), `amount_cents bigint?`, `currency text DEFAULT 'USD'`, `effective_on date?`, `reference text?`, `receipt_document_version_id bigint?`, `reason text?`, `recorded_by FK → users`, `recorded_at`. Composite FKs; unique `(financial_confirmation_id,revision)`, positive revision, nullable cents >=0, currency=`USD`. Amount/date/reference may be unknown; correction must retain old revision and include reason. **Index:** `(matter_id,kind)` and `(financial_confirmation_id,revision DESC)`. **Example:** one of two earnest-money installments.

### `readiness_evaluations` — C; immutable readiness decision snapshot

**Columns:** `id`, `matter_id`, `matter_workflow_id`, `workflow_template_version_id`, `template_validation_event_id bigint?` (not validated), `result text` (`not_ready`,`ready`,`ready_with_exceptions`), `purpose text` (`review`,`transaction_closing`), `evaluated_by FK → users`, `evaluated_at timestamptz DEFAULT now()`, `created_at`. Composite FK to workflow ensuring the version belongs to the matter; FK to the exact validation event, with service checking it belongs to that version and is effective. Unique `(matter_id,id)`. Evaluate under a coordinated matter lock and capture the result and child rows atomically with the action; database/service validates consistency. Append-only; a historical snapshot is not rewritten when facts or validation change. Current readiness remains derived from current records. Only generate review snapshots for explicit review actions and closing, not every screen refresh. **Index:** `(matter_id,evaluated_at DESC,id DESC)`. **Example:** ready with exceptions at transaction closing.

### `readiness_evaluation_items` — C; immutable supporting findings

**Columns:** `id`, `matter_id`, `readiness_evaluation_id`, `requirement_id bigint?`, `issue_id bigint?`, `incident_id bigint?`, `exception_revision_id bigint?`, `finding_kind text` (`requirement`,`issue`,`incident`,`template_validation`,`primary_attorney`), `outcome text` (`satisfied`,`not_satisfied`,`not_applicable`,`unresolved`,`nonblocking`,`blocking`,`excepted`), `description_snapshot text`, `created_at`. Composite matter FKs to evaluation and applicable typed target; exact target cardinality depends on finding kind: requirement/issue/incident must match exactly one of those FKs; template-validation and primary-attorney have none; an `exception_revision_id` may accompany an excepted requirement only. Retain requirement revision/event, issue assessment, incident event, accepted evidence and approval decision links through typed children below, including negative findings and applicable source facts. Findings are snapshots, not live FKs as sole evidence of past state; capture enough immutable detail to reproduce what was assessed without copying document contents. **Index:** `(readiness_evaluation_id)`. **Example:** applicable missing certificate covered by a specific approved exception.

### `readiness_evaluation_item_sources` — C; typed snapshot provenance

**Columns:** `id`, `matter_id`, `readiness_evaluation_item_id`, `requirement_event_id bigint?`, `requirement_evidence_event_id bigint?`, `issue_readiness_assessment_id bigint?`, `unapproved_send_event_id bigint?`, `approval_decision_id bigint?`, `exception_lifecycle_event_id bigint?`, `description_snapshot text?`, `created_at`. Exactly one typed source FK, all same-matter composite; add the required `UNIQUE (matter_id,id)` to each parent and evaluation item. Service verifies source corresponds to the item's actual target and decision; store source identities and descriptive snapshot to retain context. Review retention and access restrictions before implementation. **Index:** `(readiness_evaluation_item_id)` and each FK. **Example:** accepted evidence event or attorney approval event.

### `closing_readiness_records` — C; readiness captured for an actual closing

**Columns:** `id`, `matter_id`, `closing_event_id`, `readiness_evaluation_id`, `not_ready_reason text?`, `recorded_by FK → users`, `recorded_at`. Composite FKs; unique `(closing_event_id)`, unique `(readiness_evaluation_id)`; validate closing event is actual transaction closing, evaluation purpose is `transaction_closing` and both belong to the same matter. If snapshot result is `not_ready`, require nonblank reason, raise an audit/attention flag for attorney follow-up, and preserve it as Not Ready; do not fabricate approval or a Ready result. This is a recommended **recording** path for an event that actually happened, not authorization to proceed with an unready closing. Any review/follow-up actions use the standard issue/incident mechanisms; firm policy on any further authorization remains subject to attorney validation. Evaluate and record closing plus snapshot in one database transaction under matter lock; an external closing can occur independently of the app. Existing-matter historical entry needs an explicit historical marker and may have unknown past readiness; do not fabricate a past evaluation. **Indexes:** `(matter_id,recorded_at DESC)` and FK indexes. **Example:** recorded closing with explicit Not Ready reason.

**Recommended readiness evaluation order:** (1) evaluate current template validation and active authorized primary attorney, (2) evaluate each applicable requirement and accepted current evidence, (3) block on unresolved applicability that could affect closing, (4) evaluate open issue assessments and explicitly flagged unapproved-send blockers, (5) apply only effective attorney-approved exceptions for their exact eligible requirements, (6) report `not_ready` if any blocker remains, otherwise `ready_with_exceptions` if an effective exception is used, else `ready`. A non-waivable applicable unmet requirement or stale exception remains a blocker. Capture reason(s) per finding. Completed/resolved post-closing work is not a pre-closing readiness prerequisite unless an attorney-validated template explicitly says so; file closure separately requires disposition of open obligations. All checklist content remains provisional until attorney validation.

## 5. Documents, checklist requirements, and evidence

### `documents` — C; logical document

**Columns:** `id`, `public_id`, `matter_id`, `document_category_id FK → document_categories`, `other_category_description text?`, `title text`, `created_by FK → users`, `created_at`, `updated_at`, `row_version`, `is_historical boolean DEFAULT false`, `historical_note text?`. Unique `(matter_id,id)`; nonblank title. A pre-launch historical document may be added to a closed file with clear labeling, provenance and audit; it does not rewrite past readiness or closing decisions. Other category requires a nonblank description, enforced by service/constraint trigger. Changing the selected category requires a reason, records old/new values and reopens requirements using accepted evidence from the document. Renaming the catalog label alone does not reopen requirements. No `current_version_id`: latest accepted logical version must be resolved explicitly, and file/link may coexist. **Index:** `(matter_id,document_category_id)`. **Example:** signed agreement.

### `document_versions` — C; immutable file or external link representation

**Columns:** `id`, `public_id`, `matter_id`, `document_id`, `version_number integer`, `storage_kind text` (`upload`,`external`), `s3_bucket text?`, `s3_key text?`, `s3_version_id text?`, `external_url_ciphertext bytea?`, `external_url_key_reference text?`, `checksum_sha256 text?`, `size_bytes bigint?`, `content_type text?`, `provider text?`, `created_by FK → users`, `created_at`. Composite document FK; unique `(document_id,version_number)` and `(matter_id,id)`; version >0; upload requires nonblank bucket/key/version and null encrypted URL/key reference; external requires encrypted URL and key reference and null S3 fields. The service validates the plaintext URL before encryption; never log URLs or include them in reminder emails. The key-management and rotation scheme is an AWS implementation gate. Size null or nonnegative; validate checksum format if supplied. Upload and URL representations may coexist under the logical document; whether they represent identical content requires explicit association before treating as identical. S3 scan state belongs separately so immutable content metadata is not rewritten. **Indexes:** `(document_id,version_number DESC)` and relevant FK. **Example:** uploaded object with version ID.

### `document_classification_events` — C; immutable category changes

**Columns:** `id`, `matter_id`, `document_id`, `old_document_category_id FK → document_categories?` (initial classification), `new_document_category_id FK → document_categories`, `old_other_description text?`, `new_other_description text?`, `reason text`, `actor_user_id FK → users`, `occurred_at`. Composite document FK; nonblank reason for changes; initial event may use a standard nonblank creation reason. Category change and evidence/readiness reopening occur atomically. Label-only catalog changes are recorded in `reference_label_events` and do not trigger reopening. **Index:** `(document_id,occurred_at DESC,id DESC)`. **Example:** reclassify a document with reason.

### `document_access_events` — R/C; document access authorization

**Columns:** `id`, `matter_id`, `document_version_id`, `actor_user_id FK → users`, `action text` (`external_link_open_authorized`,`s3_link_issued`,`access_denied`), `occurred_at`. Composite matter FK; append-only. Log authorized matter-user access to external links, S3 link issuance, and denied attempts; never log plaintext URLs, signed URLs or content. A link-issued event does not prove a download. For nonexistent/unresolvable IDs, security logging must avoid fabricating a matter FK and avoid disclosing resource existence. **Index:** `(document_version_id,occurred_at DESC)`. **Example:** authorized S3 link issuance.

### `document_scan_events` — C/I; append-only scan outcome

**Columns:** `id`, `matter_id`, `document_version_id`, `outcome text` (`pending`,`passed`,`failed`,`error`), `scanner_reference text?`, `recorded_at`. Composite FK; service verifies target is upload. Uploaded files require a current scan result of `passed` before download or evidence acceptance; external links have no upload scan and use their own access controls. Use short-lived signed access after authorization; preserve errors and avoid sensitive payload. **Index:** `(document_version_id,recorded_at DESC,id DESC)`. **Example:** pending then passed.

### `document_copy_attestations` — C; retained copy of external evidence

**Columns:** `id`, `matter_id`, `external_document_version_id`, `upload_document_version_id`, `attested_by FK → users`, `attested_at timestamptz DEFAULT now()`, `note text?`. Composite matter FKs to document versions; unique `(external_document_version_id,upload_document_version_id)`. Service verifies the external and uploaded storage kinds and appropriate document association; either authorized role can explicitly attest that the upload is a copy. An attestation is not cryptographic proof. The upload remains unavailable until its scan passes. A failed scan flags the copy for investigation but does not invalidate separately accepted external evidence. **Indexes:** both version FKs. **Example:** S3 copy of an accepted external signed document.

### `document_status_events` — C; manual provider/document assertion

**Columns:** `id`, `matter_id`, `document_id`, `status text` (`requested`,`received`,`awaiting_signature`,`signed`,`rejected`,`unavailable`,`other`), `note text?`, `actor_user_id FK → users`, `occurred_at`. Composite FK; manually asserted, not provider verification. **Index:** `(document_id,occurred_at DESC,id DESC)`. **Example:** manually marked signed.

### `matter_requirements` — C; actionable checklist item independent of evidence

**Columns:** `id`, `public_id`, `matter_id`, `matter_workflow_id bigint?`, `requirement_template_id FK → requirement_templates?` (manual item), `title text`, `kind text` (`document`,`task`,`other`), `applicability text` (`applicable`,`inapplicable`,`unresolved`), `status text` (`open`,`satisfied`,`canceled`), `is_required boolean`, `is_nonwaivable boolean`, `created_by FK → users`, `created_at`, `updated_at`, `row_version`. Unique `(matter_id,id)`; `NOT is_nonwaivable OR is_required`; composite FK to workflow. Template/workflow/version consistency must be enforced via composite FKs or a constraint trigger; manual/template provenance exactly defined at migration. Partial unique `(matter_workflow_id,requirement_template_id) WHERE requirement_template_id IS NOT NULL`. Attorney controls nonwaivable status; either role may change other required→optional with reason; nonwaivable must first be changed by attorney. Either authorized role may cancel a requirement with a reason; before cancellation of a non-waivable item an attorney must remove its non-waivable status. Either role may reopen a canceled or satisfied requirement with a reason; it becomes Open and prior evidence requires reassessment. Unresolved applicability that may affect closing blocks readiness. **Index:** `(matter_id,status,applicability)`. **Example:** missing certificate.

### `requirement_events` — C; history and lifecycle

**Columns:** `id`, `matter_id`, `requirement_id`, `event_type text` (`created`,`status_changed`,`required_changed`,`nonwaivable_changed`,`applicability_changed`,`canceled`,`reopened`), `old_value text?`, `new_value text?`, `reason text?`, `actor_user_id FK → users?`, `occurred_at`. Composite FK; null actor only for explicitly recorded automated origin; add `origin text` (`user`,`system`). Required/waivability changes, cancellation and reopening need nonblank reason. Append atomically with current update; enforce attorney authority for nonwaivable change. **Index:** `(requirement_id,occurred_at DESC)`. **Example:** reason for making item optional.

### `requirement_evidence` and `requirement_evidence_events` — C; accepted evidence

`requirement_evidence`: `id`, `matter_id`, `requirement_id`, `document_version_id bigint?`, `task_id bigint?`, `financial_confirmation_revision_id bigint?`, `created_by FK → users`, `created_at`; exactly one typed target (`num_nonnulls(document_version_id,task_id,financial_confirmation_revision_id)=1`), composite FKs, unique `(matter_id,id)`; prevent duplicate active associations by chosen lifecycle policy. `requirement_evidence_events`: `id`, `matter_id`, `requirement_evidence_id`, `action text` (`linked`,`accepted`,`rejected`,`withdrawn`), `reason text?`, `actor_user_id FK → users`, `occurred_at`; rejection/withdrawal requires reason. Linking is not acceptance. Replacing/rejecting accepted evidence reopens requirement and reevaluates exceptions/readiness in one locked transaction; preserve historical links. **Indexes:** `(requirement_id)` and `(requirement_evidence_id,occurred_at DESC)`. **Example:** accepted uploaded title document or recorded earnest-money confirmation revision. Financial revisions require `UNIQUE (matter_id,id)` and a composite FK; acceptance applies to the exact revision, whose status must be confirmed, while amount/date may be unknown. Multiple confirmed revisions can satisfy one requirement. Correction or withdrawal of any accepted installment reopens the whole requirement until staff reassess the evidence set. A newer document version similarly reopens the requirement, except an attested retained copy of accepted external evidence does not by itself reopen it.

## 6. Correspondence, attorney review, and exceptions

### `correspondence` — C; logical outgoing legal communication

**Columns:** `id`, `public_id`, `matter_id`, `title text`, `status text` (`draft`,`pending_review`,`changes_requested`,`approved`,`sent`,`withdrawn`), `created_by FK → users`, `created_at`, `updated_at`, `row_version`. Unique `(matter_id,id)`; status is a workflow projection, not evidence of an effective approval. **Index:** `(matter_id,status)`. **Example:** inspection response.

**Recommended correspondence workflow:** Either authorized role may create, revise, submit, withdraw or resubmit a draft, with an audit reason for withdrawal. An attorney may self-approve or decide another user's request. A pending request has exactly one terminal decision or withdrawal; decisions and request transitions are serialized with revisions and send recording. An attorney may approve, reject or request changes with comments; require a reason for rejection and changes requested. A returned or rejected request is closed and cannot later be approved; create a new review request for a new submission. Staff can withdraw instead of resubmitting. Every package change creates an immutable revision; no changed revision is authorized by an earlier approval unless an attorney records a nonmateriality decision for that exact revision. Rejected or withdrawn materiality decisions never grant approval. An attorney may revoke a prior approval with a reason, invalidating dependent nonmateriality extensions for future sends. The application records actual external sends and incidents; it cannot prevent external sending. Do not auto-send correspondence. Access and role are checked at every step. Closed files require reopening before operational correspondence changes; the explicitly allowed historical and incident paths remain available.

### `correspondence_drafts` — C; immutable package revision

**Columns:** `id`, `matter_id`, `correspondence_id`, `revision integer`, `subject text`, `body text`, `delivery_method text` (`email`,`mail`,`other`), `created_by FK → users`, `created_at`. Composite correspondence FK; unique `(correspondence_id,revision)`, `(matter_id,id)` and `(correspondence_id,id)`; positive revision. Each revision and its recipient/attachment children become immutable when created; compose it transactionally from a mutable editor buffer or create a new revision for every change. Submission references a complete frozen revision. A revision is not authorized for sending merely because it exists. **Example:** second revision of response.

### `draft_recipients` and `draft_attachments` — C; package children

`draft_recipients`: `id`, `matter_id`, `draft_id`, `recipient_kind text` (`to`,`cc`,`bcc`,`other`), `display_name text?`, `address text`, `contact_id FK → contacts?`, `sort_order integer`; composite FK to draft, unique `(draft_id,recipient_kind,address)` under a defined address normalization policy, nonblank address. Snapshot address, never derive it from changing contact. `draft_attachments`: `id`, `matter_id`, `draft_id`, `document_version_id`, `sort_order integer`; composite FKs; unique `(draft_id,document_version_id)`. Freeze both with draft; attachments use exact document versions. **Indexes:** FK columns. **Example:** buyer attorney recipient and attached document revision.

### `approval_requests` — C; review rounds with typed targets

**Columns:** `id`, `public_id`, `matter_id`, `draft_id bigint?`, `exception_revision_id bigint?`, `requested_by FK → users`, `requested_at timestamptz DEFAULT now()`, `status text` (`pending`,`changes_requested`,`approved`,`rejected`,`withdrawn`), `row_version`. Exactly one target; composite matter FKs; unique `(matter_id,id)`. One request represents one review round; resubmission creates a new request, even for the same revision. Immutable decision events below. Service checks role and target; draft approval and exception authorization are distinct. Partial unique pending per target prevents duplicate simultaneous review requests (separate indexes for each nullable target). **Index:** `(requested_at) WHERE status='pending'`. **Example:** draft revision submitted for attorney review.

### `approval_request_events` — C; submission and withdrawal history

**Columns:** `id`, `matter_id`, `approval_request_id`, `event_type text` (`submitted`,`withdrawn`), `reason text?`, `actor_user_id FK → users`, `occurred_at`. Composite request FK; require nonblank reason for withdrawal. Either authorized role may withdraw a pending request or a returned/closed review workflow without deleting the decision; once decided, withdrawal is a new correspondence-level disposition and must not alter the historical decision. Current pending request status and event update atomically. **Index:** `(approval_request_id,occurred_at DESC,id DESC)`. **Example:** Operations withdraws an unneeded returned draft.

### `approval_decisions` — C/R; immutable attorney decisions

**Columns:** `id`, `matter_id`, `approval_request_id`, `decision text` (`approved`,`rejected`,`changes_requested`), `comment text?`, `attorney_user_id FK → users`, `decided_at timestamptz DEFAULT now()`. Composite request FK; unique `(approval_request_id)` and `(matter_id,id)`. Require a nonblank comment for rejection or changes requested. Attorney role and active authorization verified at decision time under lock; request state and decision inserted atomically. New review round uses new request. **Index:** `(matter_id,decided_at DESC)`. **Example:** approval of draft v2.

### `correspondence_materiality_decisions` — C; later revision linked to approval

**Columns:** `id`, `matter_id`, `draft_id`, `approval_decision_id`, `attorney_user_id FK → users`, `is_material boolean`, `reason text`, `decided_at timestamptz DEFAULT now()`. Composite FKs to draft and approval decision; unique `(matter_id,id)`; reason nonblank. Service verifies same correspondence, prior decision is an effective approved draft, and target revision differs and follows the approved one. A nonmaterial decision extends that approval only to the specified target revision; material means a new approval is needed. Resolve multi-revision comparison explicitly in service; no inference from labels. **Index:** `(draft_id,decided_at DESC)`. **Example:** attorney accepts typo correction as nonmaterial.

### `approval_revocations` — C; append-only revocation

**Columns:** `id`, `matter_id`, `approval_decision_id`, `attorney_user_id FK → users`, `reason text`, `revoked_at timestamptz DEFAULT now()`. Composite FK, unique `(approval_decision_id)`, nonblank reason. Attorney revokes the underlying approval and all dependent nonmaterial extensions; lock approval during send recording. Prior send records remain historical. **Example:** newly discovered issue invalidates approval.

### `correspondence_sends` — C; external sends and pre-launch history

**Columns:** `id`, `matter_id`, `correspondence_id`, `draft_id bigint?`, `approval_decision_id bigint?`, `materiality_decision_id bigint?`, `entry_kind text` (`current`,`historical`), `sent_at timestamptz?`, `sent_on date?`, `sender_user_id FK → users?`, `external_sender text?`, `method text`, `reference text?`, `historical_note text?`, `cutoff_on date?`, `attesting_attorney_id FK → users?`, `attested_at timestamptz?`, `entered_by FK → users`, `recorded_at`. All matter-scoped FKs composite. Current sends require exact draft, approval, sender, `sent_at` and no historical attestation; optional materiality decision must match target and underlying approval. Historical sends may have unknown sender and date; require either a known date before recorded cutoff or attorney attestation of pre-launch status when date unknown. Record the cutoff used and separately flag entries for review on cutoff change. Preserve historical evidence via supporting matter-scoped document links in `correspondence_send_evidence`. Define recipient snapshots below; no implied approval of historical entries. Multiple current sends allowed. Service verifies effective approval, nonrevocation, same correspondence and authorization under lock. External sending is outside the application; record what occurred, and use the separate audited incident path for a send without required prior approval; do not silently label it historical. **Indexes:** `(correspondence_id,recorded_at DESC)`, `(matter_id,sent_on)`. **Example:** approved draft sent twice, two rows.

### `unapproved_send_incidents` — C; honest record of a current send without required approval

**Columns:** `id`, `public_id`, `matter_id`, `correspondence_id`, `draft_id bigint?` (unknown or unregistered), `sent_at timestamptz?`, `sent_on date?`, `sender_user_id FK → users?`, `external_sender text?`, `method text`, `description text`, `is_readiness_blocker boolean DEFAULT false`, `status text DEFAULT 'awaiting_review'` (`awaiting_review`,`reviewed`,`disposed`), `recorded_by FK → users`, `recorded_at`, `updated_at`, `row_version`. Composite matter FKs; nonblank description; at least one of sent_at/sent_on where known, with unknown date allowed and explicitly noted. Either authorized role records an incident without asserting prior approval. Unreviewed incidents appear in attorney queue and block readiness only if staff mark them as blockers; either role may set/clear blocker with reason in `unapproved_send_events`. File closure requires attorney review or attorney-authorized disposition with reason, regardless of blocker status. The incident must not be represented as historical or an approved send. It may be recorded and reviewed while a file is closed; if follow-up work is needed, reopen with a reason before creating operational tasks. **Indexes:** `(matter_id,status)`, `(recorded_at) WHERE status='awaiting_review'`. **Example:** letter already sent without approval.

### `unapproved_send_events` and `unapproved_send_followup_tasks` — C; incident review and action history

`unapproved_send_events`: `id`, `matter_id`, `incident_id`, `event_type text` (`recorded`,`blocker_set`,`blocker_cleared`,`reviewed`,`disposed`), `outcome text?`, `notes text?`, `reason text?`, `actor_user_id FK → users`, `occurred_at`; composite incident FK; nonblank reason for blocker changes and disposition, outcome required for review, only attorney may review or authorize disposition. Preserve event and update current incident atomically. `unapproved_send_followup_tasks`: `id`, `matter_id`, `incident_id`, `task_id`; composite FKs, unique `(incident_id,task_id)`. Review records outcome, notes, reviewer, time and any follow-up tasks; it does not retroactively approve the send. Add `UNIQUE (matter_id,id)` to incidents. **Indexes:** incident event timeline and reverse task lookup. **Example:** attorney review with assigned follow-up.

### `correspondence_send_recipients` and `correspondence_send_evidence` — C; send snapshots

Recipients: `id`, `matter_id`, `send_id`, `recipient_kind text`, `address text`, `display_name text?`; composite FK to send (support `UNIQUE (matter_id,id)` there); nonblank address; copy actual recipient, compare with approved package. Evidence: `id`, `matter_id`, `send_id`, `document_version_id`, `note text?`; composite FKs; unique `(send_id,document_version_id)`. Historical recipient information may be incomplete: zero rows means unknown, not nobody. **Indexes:** send and document FKs. **Example:** actual address and archived letter.

### `exception_requests` and `exception_revisions` — C; specific waiver/override proposal

`exception_requests`: `id`, `public_id`, `matter_id`, `kind text` (`task_waiver`,`closing_override`), `status text` (`draft`,`pending`,`approved`,`rejected`,`withdrawn`,`no_longer_needed`,`review_required`,`revoked`), `requested_by FK → users`, `created_at`, `updated_at`, `row_version`; unique `(matter_id,id)`. `exception_revisions`: `id`, `matter_id`, `exception_request_id`, `revision integer`, `justification text`, `conditions text?`, `created_by FK → users`, `created_at`; composite FK, unique `(exception_request_id,revision)` and `(matter_id,id)`, positive revision and nonblank justification. Immutable submitted revisions and affected targets; approval request points to revision. For task waiver target task; closing override targets specific requirements. Exactly one appropriate typed target is required via child target validation at submission; supports multiple targets where authorized. Nonwaivable requirements cannot be overridden. Either role may withdraw a pending request or mark an approved exception No Longer Needed, with reason and retained history. If the requirement later reopens, prior approval cannot automatically reactivate; attorney review is required. An attorney may revoke an approved closing exception or task waiver with reason; atomically recalculate readiness and return a waived task to Not Started while preserving prior history. **Indexes:** `(matter_id,status)`, `(exception_request_id,revision DESC)`. **Example:** certificate exception with follow-up condition.

### `exception_lifecycle_events` — C; withdrawal, review and revocation

**Columns:** `id`, `matter_id`, `exception_request_id`, `event_type text` (`withdrawn`,`no_longer_needed`,`review_required`,`revoked`), `reason text`, `actor_user_id FK → users?` (system-generated review flag), `occurred_at`. Composite matter FK; nonblank reason. Either role may withdraw a pending request or mark an approved exception no longer needed; only an attorney can revoke approved exceptions/waivers. Reopening a satisfied requirement cannot automatically reactivate a no-longer-needed exception; flag for attorney review. On waiver revocation, update the task to Not Started and recalculate affected readiness in the same transaction. Preserve original approval and all events. **Index:** `(exception_request_id,occurred_at DESC,id DESC)`. **Example:** attorney revokes a waiver with reason.

### `exception_targets` and `exception_triggers` — C; scope and change tracking

`exception_targets`: `id`, `matter_id`, `exception_revision_id`, `task_id bigint?`, `requirement_id bigint?`; composite FKs, exactly one target, partial unique per revision/target. Service checks kind and verifies every target belongs to same matter; affected requirements always trigger review. `exception_triggers`: `id`, `matter_id`, `exception_revision_id`, `trigger_kind text` (`closing_date`,`document_evidence`), `requirement_evidence_id bigint?`, `note text?`; composite FKs; evidence required exactly for evidence trigger; unique index by revision/kind/target with `NULLS NOT DISTINCT` (PG 16). Store target and relevant fact version on decision, compare on changes, and atomically mark approved exception review-required when affected. **Indexes:** target and trigger reverse lookup. **Example:** closing date trigger.

### `exception_followup_tasks` — C; conditional authorization follow-up

**Columns:** `id`, `matter_id`, `exception_revision_id`, `task_id`; composite FKs; unique `(exception_revision_id,task_id)`. A follow-up does not by itself satisfy the original requirement. Service makes required follow-up creation atomic with conditional approval. **Example:** obtain certificate after closing.

## 7. Reminders, notifications, delivery, and audit

### `deadline_reminder_recipients` — C; configured additional recipients

**Columns:** `id`, `matter_id`, `deadline_id`, `user_id FK → users`, `is_active boolean DEFAULT true`, `created_by FK → users`, `created_at`. Composite deadline FK; unique `(deadline_id,user_id)`. Owner is derived from deadline, not duplicated here. Current active account and matter permission rechecked at send. **Index:** `(user_id,is_active)`. **Example:** extra attorney recipient.

### `reminder_occurrences` — C/I; per-recipient/channel/local-day uniqueness

**Columns:** `id`, `matter_id`, `deadline_id`, `deadline_revision_id`, `recipient_user_id FK → users`, `channel text` (`email`,`in_app`), `local_on date`, `scheduled_at timestamptz`, `status text` (`queued`,`sending`,`sent`,`suppressed`,`failed`,`uncertain`), `created_at`, `updated_at`, `row_version`. Composite deadline and revision FKs; additionally enforce revision belongs to the same deadline with `(deadline_id,id)` referenced uniqueness. Unique `(deadline_id,recipient_user_id,channel,local_on)`—do not include type or revision. `uncertain` prevents claiming exactly-once delivery; app must handle unresolved provider outcome. Store trigger reasons in child rows. On calendar/time/interval changes recalculate unsent eligible occurrences without creating duplicates; retain the settings revision used for each attempted send in an immutable schedule-history event or equivalent versioned reference. In-flight sends may have uncertain outcomes; never claim cancellation after dispatch without proof. On deadline revision suppress stale queued occurrence and allow a new candidate to reuse the daily identity if not sent, preserving history; never erase a sent attempt. Decide precise state transitions and locking in migration/service design. **Indexes:** `(status,scheduled_at)` for queue, `(deadline_id,local_on DESC)`. **Example:** owner email on local Monday.

### `reminder_occurrence_reasons` — I; multiple intervals per occurrence

**Columns:** `id`, `reminder_occurrence_id FK → reminder_occurrences`, `kind text` (`advance`,`overdue`), `days_before integer?`; unique `(reminder_occurrence_id,kind,days_before) NULLS NOT DISTINCT`; advance requires days_before >0 and overdue requires null. Preserves multiple reasons without multiple notices. **Example:** 3-day advance trigger.

### `delivery_attempts` — I/R; outbox and provider outcomes

**Columns:** `id`, `reminder_occurrence_id FK → reminder_occurrences`, `attempt_number integer`, `provider text` (`ses`,`internal`), `provider_message_id text?`, `status text` (`started`,`accepted`,`delivered`,`failed`,`uncertain`), `error_code text?`, `started_at timestamptz`, `finished_at timestamptz?`; unique `(reminder_occurrence_id,attempt_number)`, positive number. Store minimal errors; provider acceptance differs from delivery. Append-only or append separate delivery outcome events so provider callbacks do not silently rewrite history. Retry only while eligible that local day; alert after exhaustion. **Index:** `(reminder_occurrence_id,attempt_number DESC)`; unique provider IDs only if provider contract supports it. **Example:** SES accepted, later delivery outcome unknown.

### `notifications` — C; in-app inbox

**Columns:** `id`, `public_id`, `matter_id`, `recipient_user_id FK → users`, `reminder_occurrence_id FK → reminder_occurrences?`, `kind text`, `created_at`, `seen_at timestamptz?`. Unique `(reminder_occurrence_id)` when nonnull; verify occurrence recipient, matter and `in_app` channel via composite FK or service/trigger. Query always applies current matter access; seen is per recipient. **Index:** `(recipient_user_id,created_at DESC)`. **Example:** overdue deadline inbox item.

### `task_assignment_notification_items` — C; grouped in-app assignment notice

**Columns:** `id`, `matter_id`, `notification_id`, `task_id`, `assignment_event_id bigint`, `created_at`. Composite FKs to notification, task and task assignment event; unique `(notification_id,task_id,assignment_event_id)`. The service verifies the assignment event belongs to the task and enforces notification recipient/matter access. Initial assignments and reassignments notify the new owner in-app; reassignments or unassignments notify the prior owner if still authorized. Do not notify the actor as the new owner on self-assignment, but still notify an eligible previous owner. Automatic workflow assignments group tasks into one notice per recipient and matter per activation event; use a durable activation/event idempotency key and group membership, and create items transactionally. No assignment emails. For notices not grouped, the same table may hold one task. Add appropriate same-matter uniqueness and composite FKs to `notifications` and `task_assignment_events`; store old/new owners in typed task-assignment history rather than solely text events. **Indexes:** `(notification_id)`, `(task_id)`, `(assignment_event_id)`. **Example:** one activation notice linking three assigned tasks.

### `outbox_events` — I/R; transactional asynchronous intent

**Columns:** `id`, `event_key uuid` unique, `event_type text`, `matter_id bigint? FK → matters` (firm-wide event), `payload jsonb`, `status text` (`queued`,`processing`,`published`,`retry`,`dead`), `available_at timestamptz`, `lease_until timestamptz?`, `attempt_count integer DEFAULT 0`, `created_at`, `updated_at`. Nonnegative attempts; versioned minimal payload with no legal content. Worker uses `FOR UPDATE SKIP LOCKED`, bounded leases and idempotent consumer keys; event publication and DB updates cannot guarantee exactly once across AWS. **Index:** `(available_at,id) WHERE status IN ('queued','retry')`. **Example:** event announcing a reminder occurrence.

### `audit_events` — C/R; append-only activity

**Columns:** `id`, `matter_id bigint? FK → matters` (firm-wide changes), `actor_user_id FK → users?` (system/bootstrap), `origin text` (`user`,`system`,`bootstrap`), `action text`, `entity_type text`, `entity_id bigint?`, `request_id uuid?`, `changes jsonb?`, `occurred_at`. Nonblank action/type; user origin requires actor. Entity ID is descriptive audit metadata, not a substitute for relational FKs; it may outlive the source. Redact sensitive values, append-only grants/triggers, audited within business transaction; privileged DB admins can still tamper, so independent immutable export if required. **Indexes:** `(matter_id,occurred_at DESC)`, `(actor_user_id,occurred_at DESC)`. **Example:** required flag changed with reason.

## 8. Invariants and transactional boundaries

1. **Activation:** serialize on matter; check activated type, named client, primary property address/city IL and assigned active attorney; bind exactly one published matching workflow, instantiate requirements and tasks with stable unique template keys, write lifecycle/audit. Retrying cannot duplicate rows. Drafts may omit the activation facts. Property values and snapshots used for applicability must be consistent in the same transaction.
2. **Authorization and history:** services verify Workspace and matter access on every operation. App role cannot alter immutable definitions, revisions, decision records or audit history; least-privilege DB roles and triggers enforce immutability, including child rows. `updated_at` trigger is database-owned; optimistic locks are service-owned. A historical record cannot prove an event actually predated launch: retain attestation, cutoff used, actor and review status, and handle unauthorized current sends transparently under firm policy.
3. **Approval chain:** lock draft/request/approval when making a decision or recording a send; verify same matter, correspondence, target revision, attorney authority, materiality decision and revocation. Store immutable recipient and attachment snapshots. A later revocation blocks new authorized send records; actual external sends cannot be prevented by the application. Record an already-sent unapproved message as an incident, require attorney review or attorney-authorized disposition before file closure, and do not falsely assert approval.
4. **Requirements:** acceptance, evidence rejection/replacement, nonwaivable/required changes, task waiver, exception decisions and readiness recalculation are serialized on matter or the affected rows in a fixed lock order. Current readiness is derived; an unvalidated or withdrawn template, an unassessed open issue, and absence of an active authorized primary attorney with matter access each make it Not Ready. Requirements/targets and evidence cannot cross matters. If a selected trigger or affected requirement changes, flag exception `review_required` before showing readiness; unresolved nonwaivable items cannot be overridden.
5. **Dependencies and versions:** serialize task graph modifications before cycle checks; parent publication and child modification acquire compatible parent locks so definitions cannot change during publication. Insert current deadline plus initial revision; every edit locks and increments revision and writes an audit event and notification intent atomically.
6. **Cancellation/reminders:** cancel transaction and suppress existing reminders atomically; reopen file does not undo canceled transaction or resume reminders. Staff explicitly reactivate relevant reminders. Dispatch locks daily occurrence, rechecks revision, status, suppression, recipient status and permission immediately before send. External provider calls cannot be atomic with database commits; record uncertainty and avoid asserting guaranteed exactly-once sends or zero leaks after a simultaneous permission change.
7. **Matter numbering:** reserve reference independently of a rollback of the matter transaction; use unique idempotency token for retry and a non-reuse reservation record. Confirm year boundary and reservation creation concurrency in real PostgreSQL tests.

Overdue reminders run on business days. If a timed deadline passes its cutoff after the 9:00 a.m. run, its first overdue email is sent at the next eligible business-day run; dashboard status changes at the cutoff instant.

**Closed-file write boundary:** Operational mutations require reopening with a reason, including matter-specific contact corrections and follow-up tasks. Authorized hold actions and access restriction changes remain available, as do audited and labeled pre-launch historical entries and recording/attorney review of unapproved-send incidents. Historical additions do not replace earlier readiness or closing decisions. Use the immutable readiness evaluation and item records to preserve what was assessed at the time; current derived readiness is distinct. Authorization checks apply to every exception.

## 9. Indexes, access, and migration dependencies

| Access pattern | Proposed support |
| --- | --- |
| Active matter list, type/status | `matters(file_status,updated_at DESC)`, `(matter_type,file_status)` |
| Search by partial reference, legacy reference, client, address | normalized expressions and, if measured, `pg_trgm` GIN/trigram indexes; B-tree `lower()` alone does not support arbitrary `%substring%` |
| My open tasks | `tasks(assigned_to,due_on)` partial open statuses; access-filter matter join |
| Upcoming/overdue deadlines | `deadlines(due_on,matter_id)` partial `status='open'`; time/cutoff resolved in firm timezone |
| Attorney queue | `approval_requests(requested_at)` partial `status='pending'`, filtered by matter permission |
| Missing requirements, readiness | `matter_requirements(matter_id,status,applicability)` plus evidence and active exceptions by target |
| Audit timeline | `audit_events(matter_id,occurred_at DESC)`; append deterministic `id` to pagination/order indexes if timestamps tie |
| Worker pickup | `outbox_events(available_at,id)` partial queued/retry; reminder occurrence `(status,scheduled_at)` |
| User inbox | `notifications(recipient_user_id,created_at DESC)` and current matter-access checks |

Migration dependency plan: (1) DB roles and functions; (2) identity/settings/catalogs; (3) contacts/properties/matters/access and snapshots; (4) workflow definitions/execution and tasks; (5) deadlines/closing/documents; (6) requirement and evidence tables; (7) exception requests/revisions/targets, correspondence and approval tables; (8) notifications/outbox/audit; (9) add circular/forward FKs, triggers and permissions; (10) validated seeds. Cycles between approval requests and exception revisions or document references require staged `ALTER TABLE`, not circular creation assumptions.
