# Disposable PostgreSQL schema test

Run `bash tests/database/run.sh` from the repository root with Docker and Docker Compose available. The script starts a uniquely named PostgreSQL 16 Compose project with no exposed port and a temporary in-memory data directory. It applies Alembic migrations, compares the resulting baseline schema with independently applied draft SQL, checks downgrade refusal and disposable rollback/re-upgrade, tests the configured role grants and selected constraints and triggers with fictional records, and removes its own container and network on exit. Docker may need to pull the official `postgres:16` image. This is a disposable test, not a migration or a production configuration.

The script requires Docker Compose `up --wait` and builds a Python image with Alembic, SQLAlchemy and psycopg2. The test role grants are a candidate security baseline; application writes remain disabled. Do not put client data into the container. The checks exercise the draft allocation primitive, but do not verify the calling service or lost-commit recovery, all concurrent operations, application authorization, production role grants, audit completeness, recovery, performance, or production security. A test failure returns a nonzero exit status. Docker daemon and image access are required.

The suite also runs multi-session lock tests: a late party-snapshot child must wait for a sealing transaction and then fail, an earlier child must remain when sealing waits, and a workflow phase edit must fail after a concurrent publication commits. The tests observe PostgreSQL lock waits before releasing the competing operation. A temporary `NOLOGIN` probe role exercises selected denied operations; it is not a production permissions configuration. Fixtures contain fictional data and the database is destroyed after the run.

Readiness and send checks verify that another session cannot attach a child to an uncommitted parent and that insertion fails after the sealed parent commits. Reservation checks run concurrent retries using the same token and concurrent calls with different tokens, reject a retry for a different year, and confirm a separately committed allocation survives a failed matter insert. These do not test a lost connection during commit or a real service's transaction handling.

Reservation recovery tests terminate a backend after allocation but before commit and verify rollback and retry; terminate another after a confirmed server commit and verify the token returns the same allocation; race one token across two years; verify independently initialized year counters; and race two matter inserts for one allocation. The post-commit disconnect is not a simulation of losing the COMMIT response, and year-counter tests do not validate a real timezone boundary or calling service.
